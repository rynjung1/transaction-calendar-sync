# Transaction Calendar Sync

*Syncs bank transactions to the user's calendar as timestamped, location-tagged spending events.*

**Repo**: https://github.com/rynjung1/transaction-calendar-sync

## What this app does
Connects to the user's bank account via Plaid, pulls transaction data (merchant, amount, timestamp, category), and writes each transaction as an event on the user's device calendar (whichever calendar they choose — Google, iCloud, or local — via the native calendar API). The goal: a passive spending diary that shows up automatically on the calendar you already check.

## Target platforms
- iOS only. Was originally iOS + Android; changed in hindsight — user doesn't have an Android device to test on. Android config in `mobile/app.config.ts`/`eas.json` is left in place (permissions, adaptive icon assets, build profile) as harmless dead weight rather than stripped out, in case Android gets picked back up later — don't build or test against it as an active target, and don't invest further effort keeping its config current.
- Built with Expo (React Native) + a custom dev client, using EAS Build for App Store submission. Not compatible with Expo Go — Plaid's SDK requires native modules.

## Confirmed architecture (do not deviate without discussing first)

### Frontend — `mobile/`
- Expo (React Native), TypeScript
- `react-native-plaid-link-sdk` v13+ (session-based API: `createPlaidLinkSession`, not the legacy `PlaidLink` component)
- `react-native-calendar-events` for writing to the device calendar (wraps EventKit on iOS, CalendarProvider on Android) — this is the ONLY calendar integration needed, do not build separate Google Calendar API / EventKit integrations, this library covers both
- App lets the user pick which on-device calendar to write to (calendar selection is handled by `findCalendars()` from this library)
- Android `minSdkVersion` is pinned to 26 via `expo-build-properties` (`mobile/app.config.ts`) — Plaid's Android SDK (`com.plaid.link:sdk-core`) requires it and fails the manifest merger at Expo's default of 24. Don't lower this without checking Plaid's SDK requirement first. ~~iOS deployment target hasn't been checked against Plaid's iOS SDK's own minimum~~ — resolved (see Mobile security findings): no explicit override is set, so it falls through to React Native 0.86.3's own Podfile default of `15.1`, which exactly matches Plaid's podspec minimum (`ios 15.1`). No conflict.
- **Runtime-verified for real, New Architecture risk resolved**: `expo-doctor` flagged `react-native-calendar-events` and `react-native-plaid-link-sdk` as untested against New Architecture (the only architecture available at RN 0.86.3/Expo 57 — not a toggle). Ran the actual end-to-end path on a fresh EAS development build on Simulator: sign up → sign in → Plaid Link (native SDK UI rendered, institution search showed real Canadian banks — RBC, Scotiabank, TD, BMO, CIBC, Tangerine, Desjardins, National Bank, Vancity, ATB — confirming Plaid's Canadian coverage) → sandbox institution login → `exchange-token` → calendar picker (`findCalendars()` found the Simulator's calendar) → confirmation dialog → `/api/plaid/sync` pulled 48 real sandbox transactions → all 48 written as calendar events, app UI showing "Added to calendar" per transaction. **Independently verified below the app layer**, not just trusting the UI: queried the Simulator's actual EventKit database directly (`~/Library/Developer/CoreSimulator/Devices/<udid>/data/Library/Calendar/Calendar.sqlitedb`) — confirmed exactly 48 rows in the target calendar (`DEFAULT_CALENDAR_NAME`), zero duplicates, zero missing; spot-checked event content matches the design exactly: `summary` = `"Starbucks — $4.33"` (merchant — amount format), `description` = `"FOOD_AND_DRINK"` (PFC category in notes, as decided), dates matching the sandbox data. Both libraries are confirmed working under New Architecture; this specific risk is closed.
- **Real bug hit and diagnosed during this test, not fully root-caused**: right after sign-in, `/api/plaid/status` returned 401 `"Invalid or expired session"` a few times, then succeeded on retry with the exact same persisted session and no code change. Isolated via direct curl against Supabase and the backend (both worked fine in isolation with a freshly-issued token), so the backend's `requireUser()` validation itself is not broken. Leading theory: the test account's email was confirmed via the Supabase admin API (`email_confirm: true`) rather than a real confirmation link, and that had a few minutes of propagation lag — a side effect of the test shortcut, not necessarily something a real user (who confirms via the actual email link) would hit. Not fully proven, so not marked fixed — worth adding defensive retry-on-401 in `authedFetch` regardless, since transient auth propagation lag could plausibly happen for real users too (e.g., right after a password reset).

### Backend — `backend/`
- Vercel serverless functions (TypeScript, `@vercel/node`)
- Responsibilities ONLY:
  1. Create Plaid `link_token` (must happen server-side, never in the client)
  2. Exchange `public_token` for `access_token` after Link success, store `access_token` encrypted
  3. Receive Plaid webhooks (`SYNC_UPDATES_AVAILABLE`, `ITEM_LOGIN_REQUIRED`, `ITEM_ERROR`)
  4. Call Plaid's Transactions Sync endpoint when webhook fires (or on a user-initiated refresh), return new transactions to client
- Do NOT poll Plaid on a timer — use the webhook + sync pattern (`backend/lib/plaidSync.ts`)
- `backend/api/plaid/webhook.ts` is the one endpoint that can't use `requireUser()` (Plaid has no user session) — it verifies Plaid's `Plaid-Verification` JWT instead (`backend/lib/plaidWebhookVerify.ts`: signature against Plaid's published key, `iat` freshness, and a body-hash check against the actual raw bytes received). A request that fails this check is rejected outright (401/400), not acked with 200 — unlike genuine processing errors after a request passes verification, which still return 200 to avoid Plaid's retry storms. This requires real `PLAID_CLIENT_ID`/`PLAID_SECRET` at runtime, since key lookup is a real Plaid API call.

### Backend resilience (findings from a dedicated failure-mode audit — "make sure it's actually functional and won't fail")
- **Found, deliberately not fixed — real cost exposure, not just a security nicety**: confirmed no rate limiting exists anywhere in the backend (grepped for it, checked for a `vercel.json`, found nothing). `/api/plaid/sync` triggers real Plaid `transactionsSync` API calls, billed per-call in Plaid's production pricing — any authenticated user (or someone with a stolen session token, or just a client-side bug on some future retry logic) can call this endpoint as fast as their network allows with zero throttling on our side, running up real costs or degrading service for other users. Not fixed here: a proper fix needs either a new external service (Redis/Upstash — same shape of ask as Sentry/Turnstile, which the user has been wary of committing to more of right now) or a DB-based cooldown using a new `plaid_items.last_synced_at` column, which would mean a second pending schema migration stacked on top of the RLS-tightening one already awaiting the user's manual application. Flagged clearly rather than half-built or silently skipped — this is a real, live exposure once Plaid production access is live, not a someday concern.
- **Real bug, fixed and verified with genuine Plaid-signed sandbox webhooks, not just code review**: `webhook.ts` only ever handled 2 of Plaid's 8 documented `ITEM` webhook codes (`ERROR`, `LOGIN_REPAIRED`) — confirmed the full list by reading Plaid's own Items API docs. Missing `USER_PERMISSION_REVOKED`/`USER_ACCOUNT_REVOKED` (the user revokes access from their bank's own side, not through this app) meant an Item could be completely dead at Plaid's end while `plaid_items.status` stayed `"active"` forever: `/api/plaid/status` kept reporting the connection as healthy (`needsReauth` never fires for a still-"active" item), and `/api/plaid/sync` kept trying to sync a permanently-revoked Item on every call indefinitely. Fixed by mapping both codes to the existing `"error"` status — reuses `needsReauth`'s existing "not active" check with no schema change, and correctly points the user at the same reconnect path `login_required` already does. Verified for real: fired genuine Plaid-signed sandbox webhooks via `/sandbox/item/fire_webhook` for both codes against the real production endpoint and confirmed `status` flipped to `"error"` each time, then restored cleanly. Plaid's own docs additionally recommend deleting stored data associated with the Item for these two codes specifically (the access token is already dead at Plaid's end) — deliberately not done: `access_token_encrypted` is a `NOT NULL` column, so clearing it needs its own schema migration, and deleting the `plaid_items` row outright would cascade-delete the user's own transaction/Insights history over a bank-side event they didn't cause. Marking the item unusable now; a more thorough remediation is a real, deliberately-deferred follow-up, not silently skipped.
- Also confirmed and verified live: `PENDING_DISCONNECT` (US/CA-specific — this project's actual market, a 7-day advance warning before an Item stops working) is now logged (`console.warn`, confirmed appearing in real Vercel logs after firing a real sandbox webhook) rather than fully silent, but deliberately does not change `status` — doing so would stop `sync.ts` from syncing an Item that still works fine for up to 7 more days (it only syncs `status="active"` items), trading a real, avoidable transaction-history gap for an early warning that has nowhere to surface anyway (no UI currently distinguishes "about to need reconnecting" from "already broken"). A real fix needs a genuine schema addition (a distinct status, or a separate needs-attention-by timestamp) to warn without also halting sync — not implemented, flagged rather than half-built.
- **Critical real bug, partially fixed — the common case is closed, a narrower gap remains and is logged rather than silent**: `syncPlaidItem` only ever read `transactionsSync`'s `added` array; `modified` and `removed` (confirmed real fields on the SDK's own `TransactionsSyncResponse` type) were silently discarded entirely. Plaid's documented pattern for an ordinary pending→posted transition — the normal lifecycle of most card transactions, not an edge case — delivers the pending transaction's id in `removed` and the posted version in `added` under a brand-new `transaction_id`; since the two don't collide, this created a genuine second calendar event for the same real-world purchase whenever the pending version had already been synced. Fixed for the common case: a transaction still `"pending"` in our own table (never yet handed to mobile to write to a device calendar) is now cleanly deleted on `removed` or updated in place on `modified` — zero user-visible effect either way, since nothing was ever shown to the user for it yet. Verified against the real test database (not a hand-copied reimplementation) with 4 cases: pending+removed → deleted; synced+removed → preserved (can't be silently discarded, the device event still exists); pending+modified → fields updated in place; modified with no matching row → safe no-op. **Not fixed**: a transaction already synced to a real calendar event that Plaid later modifies or removes (a posted charge disputed/reversed, a settlement amount correction) — the device-side event can't be touched from the backend alone without mobile-side support (updating/deleting via `react-native-calendar-events`) that doesn't exist yet. Now logged loudly (`console.warn`) when this happens instead of silently doing nothing, so the gap is observable — a real follow-up feature, not something to silently claim as fully solved.
- **Real bug, fixed**: the cursor update on `plaid_items` was a blind write — two concurrent syncs for the same item (a webhook redelivery racing a pull-to-refresh, or racing itself) each read their own starting cursor independently and both wrote their own progress at the end with no check; whichever finished last won, even having advanced less far than a faster concurrent pass. Fixed with a real compare-and-swap (`UPDATE ... WHERE id = ? AND cursor = ?`, checking affected-row count) — at most one of two racing writers can advance the cursor per page; the other gets zero affected rows and aborts cleanly instead of silently clobbering progress. Verified against the real database: a normal single-writer advance succeeds; a second writer using a now-stale previous-cursor value correctly conflicts and throws rather than corrupting the stored value.
- **Real bug, fixed and corroborated independently by two separate audit passes**: `syncPlaidItem` buffered every page of a multi-page `transactionsSync` pull in memory and only persisted the advanced cursor once, after the *entire* pull and its DB upsert both completed. A large initial sync (Plaid can backfill up to 24 months of history on first link) can span many pages; any interruption partway through — a thrown error, or simply the function exceeding its execution time limit — discarded every already-fetched page's progress, and the next attempt restarted the identical backlog from scratch with no guarantee of ever converging if the full pull consistently takes longer than one invocation is allowed to run. Fixed: the cursor is now checkpointed after each individual page's `added`/`modified`/`removed` are all durably persisted, not once at the very end — an interruption now only ever costs the one page in flight. Verified live in production: ran a real sync through the rewritten loop and confirmed both a correct response and an intact, valid stored cursor afterward.
- **Real bug, fixed**: `PLAID_ENV` was read with a fallback (`?? "sandbox"`) but never validated against the SDK's actual supported values — confirmed by reading the installed SDK source that this version's `PlaidEnvironments` only defines `production` and `sandbox`; Plaid retired the old `development` environment, a name still common in older guides. Setting `PLAID_ENV=development` would have silently produced `basePath: undefined` with no startup error, surfacing only as a confusing low-level HTTP error on the first real API call — unlike every other required env var in this codebase, which throws loudly and immediately if misconfigured. Now validated the same way.
- **Real bug, fixed**: `PLAID_WEBHOOK_URL` was read directly with no presence check, unlike every other required secret in the codebase (`PLAID_CLIENT_ID`/`SECRET`, `SUPABASE_URL`/`SERVICE_ROLE_KEY`, `TOKEN_ENCRYPTION_KEY` — all throw loudly at module load if missing). If unset, Plaid created Items with no webhook configured at all — a silent, permanent "never receives `SYNC_UPDATES_AVAILABLE`, relies on manual pull-to-refresh forever" failure mode with no log or error anywhere pointing at the cause. Now throws the same way as the others.
- **Real, low-severity bug, fixed**: `previousMonthTotal` in `/api/transactions/monthly` summed Postgres `numeric` values (serialized as bare JS numbers by PostgREST) via repeated floating-point addition with no rounding — could produce results like `1200.9999999999998` instead of the exact `1201.00` for a large enough set of rows. Now rounded to cents, since the error here is always sub-cent, unlike the general case of rounding an arbitrary float.
- **Minor input-validation gaps, fixed**: `exchange-token.ts`'s `publicToken` and `confirm.ts`'s `transactionId`/`calendarEventId` were checked for truthiness only, not type — a wrong-typed value (e.g. an object) would reach Plaid's SDK or a Postgres `uuid`-column comparison and surface as a generic 500 rather than a clean 400. Low real-world impact (these endpoints are only reachable by an authenticated user's own trusted mobile client), fixed anyway since it was cheap and correct.
- **Real bug, fixed and independently verified against the installed SDK's types**: `plaidWebhookVerify.ts` cached a webhook verification key by `kid` but never checked its `expired_at` field — confirmed this field is real and part of Plaid's `JWKPublicKey` type (`node_modules/plaid/dist/api.d.ts`), and part of Plaid's documented, required verification algorithm: a retired key (e.g. after a suspected compromise) can still validate a signature cryptographically even though Plaid has explicitly marked it no longer trustworthy. Fixed: the cache now stores `expired_at` alongside the key and `verifyPlaidWebhook` rejects outright if it's non-null. Since a `kid` that's expired stays expired permanently (never un-retires under the same id), this is also cached correctly rather than re-checked on every call.
- **Severe real bug, fixed and verified — recommend rotating `PLAID_SECRET`**: every `console.error(label, err)` call that could log a Plaid API error was logging the *raw* axios error object. Plaid's Node SDK is axios-based, and an axios error's `.config`/`.request` embed the entire outgoing request — for every single Plaid call in this app, that includes the `PLAID-SECRET` header (the one master credential for the whole Plaid integration, not scoped to a user or item) in plaintext, and for item-scoped calls (`itemRemove`, `itemGet`, `transactionsSync`) the decrypted `access_token` too. Proved this for real, not by reading axios docs: forced a genuine Plaid API error with a canary access token and a real request, logged the raw error object, and both the real `PLAID_SECRET` and the canary token appeared in the output in plaintext. This means any Plaid API failure ever hit in production — a bad access token, a transient outage, a malformed request — would have written the master secret straight into Vercel's log retention, undermining the whole point of encrypting tokens at rest. Fixed: `backend/lib/logging.ts`'s `safeErrorInfo()` extracts only `message`, `httpStatus`, and Plaid's own error response body (`error_code`/`error_type`/`error_message` — describes the failure, never echoes back what we sent) and is now used at every log site that touches a Plaid call (and, for defense-in-depth, everywhere else too). Verified against the actual shipped module with the same forced-error technique: no secret, no token, still a useful `error_code`. **Not verifiable from here whether this was ever actually triggered in real production traffic** (would require checking Vercel's log history, which I don't have access to) — rotating `PLAID_SECRET` in the Plaid dashboard is a cheap, high-value precaution given the exposure window existed since early in this project.
- **Real bug, fixed and verified live in production**: `/api/plaid/status` computed `linked` from `plaid_items` rows with `status = "active"` only. A bank needing re-authentication (Plaid `ITEM_LOGIN_REQUIRED` — a normal, expected occurrence, not an edge case) sets that item's status to `"login_required"` via the webhook (`webhook.ts`). For a user with only one linked bank, this silently flipped `linked` back to `false` — the app took that as "never linked" and routed them back through first-link onboarding, and linking again there would create a *second* Plaid item for the same bank rather than fixing the broken one, risking duplicate `synced_transactions` (dedup is per-item) once both were pulling the same account. Fixed: `linked` now means "has completed onboarding at least once" (any `plaid_items` row, any status); a new `needsReauth` field is `true` when any item isn't `active`. Mobile (`App.tsx`) shows a banner directing the user to Settings when this fires — no dedicated Plaid "update mode" reconnect flow exists yet, but relinking via Settings' existing "Add another bank account" is safe (the broken item is excluded from all future syncs by `sync.ts`'s `status = "active"` filter, so it just goes inert rather than duplicating). Verified live: forced a real test item into `login_required` via direct DB write, confirmed the production endpoint returned `{"linked":true,"needsReauth":true}` (the exact broken-before state), confirmed `/api/plaid/sync` still returned 200 with that item excluded rather than erroring, then restored the item and confirmed a clean `{"linked":true,"needsReauth":false}`.
- **Real bug, fixed**: `/api/plaid/sync` looped over a user's `plaid_items` with a bare `await syncPlaidItem(item, filters)` per item, no per-item error handling — one item throwing (a transient Plaid rate limit or network blip, not even an item-level error) failed the *entire* request with a 500, including every other healthy linked account's transactions, even though their data had often already been fetched and stored by that point. Directly undermines the multi-account feature this project added. Fixed: each item's sync is now wrapped in its own try/catch, logged and skipped on failure (that item's cursor simply isn't advanced, so it's retried next sync) rather than failing the whole request.
- **Real bug, fixed**: `exchange-token.ts` pulls an eager first batch of transactions right after creating the `plaid_items` row, so the user doesn't have to wait for Plaid's first webhook. That eager sync call wasn't wrapped in its own error handling — a transient failure there (not a linking failure at all) reported "couldn't link account" to the user even though the `plaid_items` row had already been inserted successfully, i.e. the account genuinely was linked. Worse, the user was then free to retry Link from scratch, which would create a *second* Plaid item for the same bank. Fixed: the eager sync is now best-effort (caught, logged, non-fatal) — the row insert is what actually constitutes "linked"; the regular sync path picks up the item regardless.
- Not fixed, flagged rather than silently left: no full Plaid "update mode" re-link flow exists for a `login_required` item — see the `needsReauth` entry above for the current (safe, if imperfect) workaround.
- **Checked and confirmed clean, not assumed**: `0001_init.sql`'s RLS policies grant `authenticated` SELECT on `users`/`plaid_items`/`synced_transactions` scoped to `auth.uid()` — on paper, that means a user's own session JWT plus the app's embedded publishable key could read their own row directly via Supabase's REST API, including `plaid_items.access_token_encrypted` (ciphertext, but unnecessary exposure since the mobile app never calls `supabase.from(...)` at all — confirmed by grep, it only ever uses `supabase.auth.*`). In practice this is fully blocked one layer lower: `0002_grants.sql` only ever granted table privileges to `service_role`, never to `authenticated`/`anon`, so Postgres denies the query before RLS is even evaluated. Verified live against production: direct REST reads of all three tables with a real user's own valid access token return `403 permission denied for table ...`, while the backend's service-role key still reads fine. Direct database access via the embedded key is a dead end today — but this makes the RLS policies themselves unreachable dead code resting on an easy-to-break assumption (one future `GRANT SELECT ... TO authenticated` — e.g. added for some unrelated feature — would silently reactivate them exactly as originally written, including the `access_token_encrypted` exposure). Worth tightening properly at some point (drop the SELECT policies entirely, or exclude `access_token_encrypted` via a view) rather than relying on the current grants never changing; not urgent since nothing in the deploy process would add such a grant by accident.

### Database
- Postgres via Supabase (also provides auth, so we get user accounts for free)
- Schema defined in `backend/supabase/migrations/0001_init.sql`: `users`, `plaid_items` (encrypted access_token, item_id, institution, sync cursor), `synced_transactions` (dedupe key, calendar_event_id, status)
- Backend writes with the service-role key (bypasses RLS entirely — the backend's own per-request user-scoping is the real protection there, not RLS). RLS policies exist on all three tables but are currently unreachable dead code — see the Backend resilience finding below for why, and the pending migration (`0004_drop_unused_select_policies.sql`, not yet confirmed applied) that closes the gap for good rather than relying on that staying true.

### Auth
- Supabase Auth — so a user's Plaid connection persists across app reinstalls / device changes
- Session storage moved from plain `AsyncStorage` to `expo-secure-store` (`mobile/src/lib/supabase.ts`, iOS Keychain / Android Keystore-backed) — runtime-verified on a fresh EAS build (see the runtime-verified entry under Mobile UI/UX below): real sign-up, sign-in, and persisted-session-survives-relaunch all worked against it. One real bug surfaced during that test: `/api/plaid/status` returned 401 a few times right after sign-in, then succeeded on retry with the same session and no code change — not fully root-caused (leading theory: propagation lag from confirming the test account via the Supabase admin API rather than a real email link), so `authedFetch` (`mobile/src/lib/api.ts`) now retries once via a forced session refresh on any 401 before surfacing an auth error.

### Mobile UI/UX (findings from a dedicated craft review, prompted by user doubt the app felt "vibe coded")
- **Real bug, fixed — found by tracing what account deletion actually leaves behind on-device**: `App.tsx`'s selected-calendar `AsyncStorage` key was a single global key, never scoped per user and never cleared on sign-out or account deletion. Concretely: delete your account and sign up fresh on the same device, and the brand-new account silently inherited the deleted account's calendar choice — skipping `CalendarPickerScreen`, and the privacy confirmation it shows, entirely. Same mechanism on a shared device with two different accounts: whichever signed in most recently would leave its choice for the other to inherit on next sign-in. Fixed by scoping the key to the signed-in user's id (`selectedCalendar:<user-id>`) rather than clearing-and-hoping — Supabase never reuses a deleted user's id for a new account, so a fresh signup always reads an empty key with no explicit cleanup needed, and two accounts on one device never collide. Verified with a real test: account A's stored choice stays intact but fully isolated; a brand-new account B reads `null` and correctly starts fresh.
- **Real bug found by checking the interaction between two features built this session, not caught when either shipped alone**: `HomeScreen`'s pending-events map (dedupes a retried confirm against a create that already succeeded — see below) only ever cached `eventId`, not which calendar it was created on. If a create-succeeds-confirm-fails transaction sat unconfirmed and the user then used "Change calendar" (a separate feature added this session) before the next retry, the retry would silently reuse the cached `eventId` — an event that still lives on the *old* calendar — so the transaction the user explicitly moved to a new calendar would silently stay on the one they'd just moved away from. Fixed: the cache now stores `{eventId, calendarId}`; a cached entry is only reused if its `calendarId` matches the current selection, otherwise the stale event is best-effort removed from the old calendar (`removeTransactionEvent()`, never throws — the old calendar could itself be gone) and a fresh one is created on the calendar the user actually picked. Verified with a real test covering both paths: same-calendar retry still reuses the cached event (no regression), calendar-switch retry creates fresh on the new calendar and cleans up the orphaned one.
- **Real, severe bug, fixed**: `CalendarPickerScreen` — a required gate in front of the *entire app* for every single user — rendered the exact same "No writable calendars found on this device" empty state whether there genuinely were no calendars or the user had simply tapped "Don't Allow" on the permission prompt (an entirely ordinary thing for a real user to do, not misuse). Denying permission was a permanent dead end: no retry, no path to Settings, nothing recoverable short of quitting the app, finding Settings unprompted, granting access, and relaunching from scratch. Fixed: a distinct `permissionDenied` state shows the real reason, an "Open Settings" button (`Linking.openSettings()`) gets the user there directly, and a "Try again" button re-runs the permission check on return — the standard, expected recovery loop for a denied OS permission.
- **Real bug, fixed and verified with a real timing test (including the failure mode my own fix could have introduced)**: `/api/plaid/sync` returned *every* pending transaction in one response with no limit. Under normal use this stays small, but a user who doesn't open the app for weeks — an ordinary pattern for a passive spending diary, not misuse — can accumulate a large backlog purely from Plaid's webhook-driven syncing running the whole time in the background. One huge response meant `HomeScreen`'s sequential per-transaction loop (each a real device-write-plus-network round trip) could run for a very long time before showing anything finished. Fixed with backend pagination (`hasMore`/`total`, 100 per page) and a mobile-side loop that keeps calling sync until exhausted, showing accurate progress across the whole operation rather than resetting per page. Caught a real bug in that fix before shipping it, not after: a page where *every* transaction fails (e.g. calendar access revoked mid-sync) would never actually shrink the server-side pending count, so re-fetching the "next" page would return the identical stuck page forever. Added a guard — bail once a full page confirms zero successes — and proved both behaviors with a real test: 250 pending transactions across a 100-item page size correctly took exactly 3 iterations and processed all 250; a fully-stuck page correctly broke out after exactly 1 iteration instead of looping, with everything in it honestly marked "failed" (remaining "pending" server-side for the next real attempt, not lost).
- **Real bug, fixed and independently verified as plausibly explaining an earlier unresolved mystery**: `App.tsx`'s `onAuthStateChange` callback discarded the event name entirely (`_event`) and re-armed `booting` (which unmounts/remounts the entire app behind a bare spinner) for *any* truthy session — not just a genuine sign-in. Confirmed against `@supabase/auth-js`'s actual `AuthChangeEvent` type: it also fires `TOKEN_REFRESHED` (routine, roughly hourly via `autoRefreshToken: true`), `USER_UPDATED`, and `INITIAL_SESSION`. Fixed to only re-arm on `event === "SIGNED_IN"`. This is a plausible real explanation for the transient "401 right after sign-in, fixed by retrying" symptom hit during live testing earlier — a stray re-mount racing the in-flight status check — rather than just a cosmetic flash; the retry-on-401 fix in `authedFetch` stays regardless since it's still real, correct resilience for whatever else could cause a stale token.
- **Real bug, fixed and proven with a before/after test**: `createTransactionEvent()` anchored a date-only transaction (no `datetime` from Plaid) to `${date}T12:00:00.000Z` — noon **UTC**, an absolute instant. EventKit displays a non-recurring event by converting its absolute instant to the *viewing* device's current timezone (setting `CalendarEventWritable.timeZone` doesn't change this for a single event — confirmed by reading the library's own type docs — that field mainly affects recurrence math). A user materially west of UTC saw a "noon" transaction rendered as their own early morning. Verified the exact before/after with `TZ` env var simulation: old code showed 5:00 AM in Vancouver / 9:00 PM in Tokyo for the same transaction; new code (`localNoonIso()`, building the `Date` from local components so `.toISOString()`'s local→UTC conversion round-trips correctly) shows 12:00 PM in both. Also now sets `timeZone` on the written event for correctness, though the real fix is the anchor construction, not that field.
- **Real bugs found and fixed — reentrancy guards missing beyond the one already added to `HomeScreen`**: `LinkAccountScreen`'s "Connect a bank account" only guarded with `disabled={loading}` (async React state) — the same race class already fixed elsewhere, but here a double-tap landing before re-render could start two concurrent Plaid Link sessions and, if both completed, link the *same bank* as two separate Plaid Items (two distinct public tokens exchanged), silently double-diarying every one of that bank's transactions going forward. Added the same `useRef` guard pattern as `HomeScreen`.
- **Real bug found and fixed**: `InsightsScreen`'s month-fetching had a genuine race, and it went deeper than the existing `cancelled` flag actually protected — that flag only ever guarded `setError`/`setLoading`, never the `setTransactions`/`setPreviousMonthTotal` calls inside `fetchMonth` itself, which ran unconditionally. Changing months quickly (re-firing the effect while an older fetch is still in flight) or pulling to refresh independently of the effect could let a stale, slower response overwrite a newer, faster one's data. - **Real bug, fixed (narrower in practice than first suspected — checked against the actual SDK rather than assumed)**: `confirmDeleteAccount` wrapped `deleteAccount()` and `supabase.auth.signOut()` in one try/catch, so a failure in the sign-out step after a successful deletion could report "Couldn't delete account" — a false negative on something that had already succeeded. Read `@supabase/auth-js`'s actual `_signOut` implementation: it already treats a 404/401/403 (exactly what signing out a just-deleted user produces) as expected and returns `{error: null}` without throwing, so the practical trigger is narrower than a normal network/auth hiccup — only a genuine unhandled exception (e.g. a SecureStore failure clearing the local session) would reach it. Still fixed with separate try/catch blocks, since the false-negative message would be wrong regardless of how rare the trigger is.
- **Accessibility gaps beyond what was previously marked "all fixed"**: that claim wasn't accurate app-wide — `AuthScreen` (Sign in/Sign up/Privacy Policy), `LinkAccountScreen` (Connect/Cancel), `SettingsScreen` (Save/Add account/Change calendar/Delete account — a destructive, irreversible action that had zero accessibility signal), and the `App.tsx` tab bar all had interactive elements with no `accessibilityRole`/`Label`, sitting in the same files as other elements that already had them (an incomplete pass, not a deliberate omission). - **Real bug, fixed and proven with a before/after test**: `HomeScreen.handleSync()`'s per-transaction loop called `createTransactionEvent()` (a local device write) then `confirmCalendarEvent()` (a network call) inside one try/catch. If the calendar write succeeded but the confirm call failed — a network drop or backend hiccup between the two, entirely plausible on a real phone — the transaction stayed `"pending"` server-side forever (only a successful confirm flips it to `"synced"`), so the *next* sync fetched the same transaction again and created a **second** real calendar event for it. Directly contradicts this project's own "one calendar event per transaction" constraint. Proved both the bug and the fix with a standalone logic test (mocking just the AsyncStorage/network calls, not the RN runtime): the old loop created a second `event-2` on retry with `event-1` left orphaned on the device; the new loop persists `{transactionId: eventId}` to `AsyncStorage` (`mobile/src/screens/HomeScreen.tsx`'s `PENDING_EVENTS_KEY`) right after a successful create and *before* attempting confirm, so a retry (later in the same sync, or an entirely new one) reuses the existing event and only retries the confirm call — createCallCount stayed at 1 across two passes where confirm failed then succeeded, verified explicitly, not assumed.
- **Real bug, fixed**: `AuthScreen`'s `handleSignIn`/`handleSignUp` had zero client-side validation — caught live during actual end-to-end testing, not hypothetically: submitting a blank email calls Supabase with an empty string, which it treats as an anonymous-sign-in attempt and rejects with `"Anonymous sign-ins are disabled"`, a real but meaningless message to someone who just forgot to type an email. Fixed with a trivial local check before either call.

### Observability
- **Real gap, being closed**: unlike the backend (which has real, if basic, visibility via Vercel's own log retention — that's how the `PLAID_SECRET`-leak bug earlier this session was actually found), the mobile app had zero crash/error reporting. If something broke for a real user on their own phone, there was no way to find out short of them explicitly saying so. Added `@sentry/react-native` (`~7.11.0`, matched to Expo SDK 57 via `expo install`), initialized in `index.ts` before anything else (`initSentry()`) plus wrapped with `Sentry.wrap(App)` for a React error boundary — together these catch both uncaught async exceptions and render-time crashes automatically, no other code changes needed. `mobile/src/lib/sentry.ts` reads the DSN from `app.config.ts`'s `extra.sentryDsn` (a DSN is a *publishable* identifier by Sentry's own design — safe to embed the same way as the Plaid/Supabase values already there, it only lets a client send events, not read/manage the project) and no-ops safely on an empty one, so this is safe to ship before a real Sentry project exists. Performance tracing (`tracesSampleRate`) is deliberately `0` — a separate, quota-consuming thing from error reporting, not turned on as a side effect of the actual ask. **Not yet complete**: the DSN itself is still an empty placeholder — the user is creating a free Sentry account; once they provide the real DSN it goes into `app.config.ts`, and since this is a new native dependency, needs a fresh EAS build to actually take effect (same pattern as `expo-secure-store` earlier this session — a JS-only Metro reload isn't enough for a new native module). `expo-doctor` run after installing: no new issue introduced (the one pre-existing New-Architecture warning is unrelated and already verified live).

### Mobile security (findings from a dedicated review)
- **Real, documented gap being closed — Cloudflare Turnstile brute-force protection**: checked Supabase's own docs and community-reported pentest findings directly rather than assuming Supabase's defaults were sufficient — Supabase Auth's built-in rate limiting is IP-based only (a token-bucket allowing bursts up to ~30 requests), and its CAPTCHA-based "Attack Protection" is **off by default**; confirmed this project has it off too, since `AuthScreen.tsx` never sent a `captchaToken` before this change. Built the mobile-side half: `mobile/src/components/TurnstileChallenge.tsx` (a `react-native-webview`-hosted Cloudflare Turnstile widget — there's no native RN SDK, this is the standard approach) exposes an imperative `execute()` returning a token, wired into both `signInWithPassword`/`signUp` via `options.captchaToken`. Confirmed by reading `@supabase/auth-js`'s own source that passing `captchaToken: undefined` (the not-yet-configured state) serializes identically to omitting it — safe to ship before Turnstile exists. Reads the site key from `app.config.ts`'s `extra.turnstileSiteKey` (empty placeholder currently) the same way `sentryDsn` works — a Turnstile *site* key is meant to be public by Cloudflare's own design, unlike the *secret* key, which goes directly into Supabase's dashboard and never touches this codebase. **Not yet complete**: needs the user to create a free Cloudflare Turnstile widget (site key comes here), and separately toggle Supabase's dashboard Attack Protection setting with the corresponding secret key (their side, not something I can do) — then needs a fresh EAS build since `react-native-webview` is a new native dependency.
- **App Store blocker — fixed and verified end-to-end, not assumed**: `expo-dev-client`'s launcher screen used to ship in *every* EAS build profile, including `production` (the `eas.json` `developmentClient` flag has no effect on this). Traced through `expo-dev-launcher`'s `EXDevLauncherController.m` and confirmed empirically: excluding `"expo-dev-client"` from `app.config.ts`'s `plugins` array alone is **not sufficient** — it left the generated `AppDelegate.swift` byte-identical, because CocoaPods autolinking (`use_expo_modules!` in the generated Podfile) links every Expo native module found in `node_modules` regardless of the `plugins` array, and that's what actually wires `expo-dev-launcher`'s AppDelegate-subscriber hook into the autolinking-generated `ExpoModulesProvider.swift`. The real fix is `mobile/plugins/withExcludeDevClientFromProductionAutolinking.js`, applied only when `EAS_BUILD_PROFILE === "production"` (`mobile/app.config.ts`, which replaced the old static `app.json`): it passes `exclude: ['expo-dev-client', 'expo-dev-launcher', 'expo-dev-menu']` to `use_expo_modules!`. Verified by running real `expo prebuild` both ways: production profile → zero `DevLauncher`/`DevMenu` references in `ExpoModulesProvider.swift` and `Podfile.lock`; no profile set (normal local dev) → both present as before. `expo-updates` deliberately stays in all profiles including production (legitimate for real OTA updates) — only the interactive dev-launcher UI is excluded.
- **Calendar privacy — mitigated, not eliminated**: `createTransactionEvent()` (`mobile/src/lib/calendar.ts`) still puts the merchant name and exact dollar amount directly into the calendar **event title** — that's the app's core feature, not something to remove. What's fixed: `CalendarPickerScreen.tsx` now confirms with the user before writing to a calendar, naming the actual calendar and its source and spelling out exactly what becomes visible. Checked `react-native-calendar-events`'s `Calendar` type first — no field indicates whether a calendar is actually shared (title/source/isPrimary/allowsModifications only), so this can't be auto-detected and gated only for the risky case; the confirmation runs every time instead, which is fine since this screen only appears once per calendar choice.
- Passed cleanly, checked directly rather than assumed: no `NSAppTransportSecurity`/`NSAllowsArbitraryLoads` exceptions weakening TLS in `app.config.ts`; no custom `Linking`/deep-link handling in the app's own code that could act on attacker-controlled URL parameters (Supabase client has `detectSessionInUrl: false`).
- The 11/5 `npm audit` warnings in `mobile/`/`backend/` (uuid buffer-bounds bug via `xcode`→`@expo/config-plugins`; `ajv`/`path-to-regexp`/`undici` via `@vercel/node`) are real CVEs but confirmed build-tooling-only — every `@vercel/node` import in `backend/` is `import type` (erased at compile time, never executed), and the vulnerable mobile chain only runs during `expo prebuild`, never shipped in the app bundle. `npm audit fix --force` in both cases suggests a major-version *downgrade* (Expo 46, `@vercel/node` 4.0.0) — do not apply it, it would break the app for no real security gain. Not re-litigating this without new evidence.
- **Found, deliberately not implemented, flagged as a likely real blocker for actual Canadian banks**: `linkTokenCreate` never sets `redirect_uri`, and there is no code anywhere in the mobile app to receive an inbound OAuth-redirect deep link — confirmed by checking Plaid's own SDK README (lists OAuth redirect URIs as required Link/Dashboard setup) and grepping the whole mobile codebase (the only `Linking` call anywhere opens the privacy-policy URL outbound; nothing handles an inbound redirect). This matters specifically because most major Canadian banks (several of which appeared right in this app's own institution-search screen during the live end-to-end test — RBC, TD, Scotiabank, BMO, CIBC) commonly require OAuth-based Plaid Link, unlike the sandbox test institution used for that test. Not fixed here: needs a `redirect_uri` registered in the Plaid Dashboard (an account action, not a code change I can make alone), a URL scheme/associated-domain configured for the app to receive the redirect, and `react-native-plaid-link-sdk`'s specific OAuth-continuation handling on relaunch — a real, scoped feature, not a quick patch.
- **Found, deliberately not fixed, long-term risk documented rather than silently carried**: `react-native-calendar-events` (the app's only calendar-write library, and the thing the whole product depends on) is confirmed upstream-abandoned, not just "untested against New Architecture" as previously recorded — `2.2.0` (pinned here) is both the last version ever published (2022-06-26) and the newest that has ever existed on npm, and the library's own GitHub repo states verbatim: "This repository is deprecated and no longer supported." It works today — proven by this session's own live, independently-verified end-to-end test (48/48 real calendar events, confirmed in the actual EventKit database) — but "works today" isn't the same guarantee as "has an upstream fix path if a future iOS release breaks it," because there isn't one without forking the library or replacing it. Not an immediate action item, but a real fact to know going into any future iOS SDK upgrade. A concrete consequence of the abandonment, not just a theoretical one: iOS 17 introduced a genuinely separate "write-only" calendar permission level (`EKEntityWriteOnlyAccessToEvents`), distinct from full read/write access — checked the library's actual native source (`ios/RNCalendarEvents.m`) and it only ever calls the older `requestAccessToEntityType:` API (pre-dating iOS 17's split, consistent with a 2022 last release), with no path to request write-only. Confirmed our own code never reads existing calendar content anywhere (`findCalendars()` only returns calendar metadata — id/title/source — never event contents; the only other calls are `saveEvent`/`removeEvent`, both writes), matching what the privacy policy already claims. So the app requests broader OS permission (full access) than it actually uses (write-only), purely because the dependency never adopted the newer, more privacy-respecting API — not fixable without replacing the library.
- **Resolves a previously-open question, no code change needed**: this file used to list "iOS deployment target vs. Plaid's podspec minimum" as unverified. Traced it via source rather than guessing: `app.config.ts`'s `expo-build-properties` config only sets `android.minSdkVersion`, so iOS falls through to React Native's own Podfile default — read directly from `node_modules/react-native/scripts/cocoapods/helpers.rb`, RN 0.86.3's floor is `15.1`, exactly matching Plaid's SDK podspec minimum. No conflict. Caveat: confirmed by reading source, not by an actual `pod install`/prebuild run — worth a quick empirical confirmation on the next real build, but nothing to change.
